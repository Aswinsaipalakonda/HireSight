# HireSight Data Dictionary

Version 1.0 — matches `data/raw/` generated by `scripts/generate_dataset.py` (seed = 42).

All data is **synthetic**. No real names, emails, phone numbers, or addresses exist in
this dataset. City labels are broad illustrative Indian city labels. Currency values are
illustrative INR amounts.

## Table overview

| Table | Grain | Rows |
|---|---|---|
| `candidates` | One row per candidate | 3,512 |
| `jobs` | One row per job posting | 45 |
| `recruitment_sources` | One row per sourcing channel | 7 |
| `applications` | One row per application (**central fact table**) | 8,000 |
| `screening_results` | One row per screened application | 7,551 |
| `application_stage_history` | One row per funnel stage event | 23,835 |
| `offers` | One row per issued offer | 869 |
| `source_costs` | One row per source per month | 84 |

Relationships:

```
candidates 1──n applications n──1 jobs
recruitment_sources 1──n applications
applications 1──n screening_results
applications 1──n application_stage_history
applications 1──1 offers (one offer per application in this dataset; schema supports 1──n)
recruitment_sources 1──n source_costs
```

`application_id` is the central fact key for all funnel analysis. A candidate may submit
multiple applications.

## candidates

| Column | Type | Definition | Rules / allowed values |
|---|---|---|---|
| `candidate_id` | INT (PK) | Unique candidate identifier | 1–3512, unique, non-null |
| `experience_years` | DECIMAL(4,1), nullable | Simulated years of professional experience | 0–20; blank for ~175 rows (intentional) |
| `highest_education` | VARCHAR(60), nullable | Highest education category | BTech, BSc, BCom, BA, MTech, MBA, MCom, MSc, PhD, Diploma; blank for ~105 rows (intentional) |
| `candidate_city` | VARCHAR(80) | Broad city label | 12 fictional/broad Indian city labels |
| `created_at` | DATETIME | Synthetic candidate profile creation time | ≥ 2025-10-01, ≤ first `applied_at` of that candidate |

Known intentional quality issues: missing `experience_years` / `highest_education`;
inconsistent casing and stray whitespace in some `candidate_city` and `highest_education`
values; 12 near-duplicate profiles (IDs 3501–3512 copy the attributes of an earlier
candidate with a new ID — pairs listed in `generation_metadata.json`).

Known intentional quality issues: inconsistent casing/whitespace in a few `department`

## recruitment_sources

| Column | Type | Definition | Rules / allowed values |
|---|---|---|---|
| `source_id` | INT (PK) | Unique source identifier | 1–7, unique, non-null |
| `source_name` | VARCHAR(80) | Sourcing channel name | Employee Referral, Company Careers Page, Online Job Board, Social Media Ads, Campus Hiring, Recruitment Agency, Walk-in / Job Fair |

## applications

| Column | Type | Definition | Rules / allowed values |
|---|---|---|---|
| `application_id` | INT (PK) | Unique application identifier — **central fact key** | 1–8000, unique, non-null (no duplicates by design) |
| `candidate_id` | INT (FK → candidates) | Applicant | Must exist in candidates; not unique here (candidates may apply to several jobs) |
| `job_id` | INT (FK → jobs) | Applied-to job | Must exist in jobs |
| `source_id` | INT (FK → recruitment_sources), nullable | Acquisition channel | Blank for ~15 rows (intentional) |
| `applied_at` | DATETIME | Application timestamp | Within 2026-01-01 – 2026-12-31, ≥ job posted_date |
| `current_status` | VARCHAR(30) | Canonical current outcome | screening, interview, offer (active states); rejected, withdrawn, hired, declined (final states) |

Status semantics: `declined` = offer issued and declined by candidate. `offer` = offer
pending response. `screening` / `interview` = still in process at that stage as of the
end of the period. Active-state applications must not be counted as drop-offs.

## screening_results

One row per application that reached the screening stage.

| Column | Type | Definition | Rules / allowed values |
|---|---|---|---|
| `screening_id` | INT (PK) | Unique screening record | Unique, non-null |
| `application_id` | INT (FK → applications) | Screened application | One screening per application in this dataset |
| `screening_date` | DATETIME | Screening timestamp | ≥ corresponding `applied_at` |
| `ai_score` | DECIMAL(5,2) | **Simulated** AI screening score | Intended 0–100; ~10 raw rows are out of range (intentional, for cleaning) |
| `screening_decision` | VARCHAR(30) | Screening outcome | Pass, Review, Reject (some rows have casing/whitespace issues) |
| `score_version` | VARCHAR(30) | Synthetic scoring-model version | v1.0 (before 2026-07-01), v2.1 (from 2026-07-01) |

**Interpretation warning:** scores are simulated with deliberate overlap between
outcome groups. A high score does not cause or guarantee any outcome, and score
differences across groups cannot support fairness conclusions.

## application_stage_history

Event-history table; one row per stage event, so **one application has multiple rows**.
Never join it 1:1 to applications without aggregation care, and never sum
application-level metrics across it without deduplication.

| Column | Type | Definition | Rules / allowed values |
|---|---|---|---|
| `stage_event_id` | INT (PK) | Unique stage event | Unique, non-null |
| `application_id` | INT (FK → applications) | Owning application | Must exist in applications |
| `stage_name` | VARCHAR(40) | Funnel stage | applied, screened, interview, offer, hired, rejected |
| `stage_status` | VARCHAR(30) | Event outcome | entered, passed, failed, withdrawn (casing/whitespace issues in some rows) |
| `stage_timestamp` | DATETIME | When the event happened | ≥ previous event of the same application, except ~8 intentionally disordered rows |
| `stage_duration_hours` | DECIMAL(10,2), nullable | Hours since the previous stage event of the same application | Null for each application's first event |

Funnel reading guide: `applied/entered` → `screened` (passed/failed) → `interview`
(passed/failed/withdrawn, 1–2 events) → `offer` → `hired`. Terminal events are
`failed`/`withdrawn` on a stage event, or a `rejected`/`hired` stage event.
Pre-screen withdrawal is modelled as a second `applied` event with
`stage_status = withdrawn` (413 applications); do not double-count these applications.

## offers

One row per issued offer (869 rows: 613 accepted, 134 declined, 52 withdrawn, 70 pending).

| Column | Type | Definition | Rules / allowed values |
|---|---|---|---|
| `offer_id` | INT (PK) | Unique offer | Unique, non-null |
| `application_id` | INT (FK → applications) | Offered application | One offer per application in this dataset |
| `offer_date` | DATE | Offer issue date | Within period; ≥ application's offer-stage timestamp |
| `offered_salary_inr` | DECIMAL(12,2) | Illustrative annual salary (INR) | Between job salary_min and salary_max |
| `offer_status` | VARCHAR(30) | Offer outcome | accepted, declined, withdrawn, pending |
| `response_date` | DATE, nullable | Candidate response date | Null while pending; ≥ offer_date |

Offer acceptance rate denominator excludes `pending` offers.

## source_costs

| Column | Type | Definition | Rules / allowed values |
|---|---|---|---|
| `source_cost_id` | INT (PK) | Unique cost record | Unique, non-null |
| `source_id` | INT (FK → recruitment_sources) | Costing source | Must exist in recruitment_sources |
| `month_start` | DATE | First day of the cost month | 2026-01-01 … 2026-12-01, one row per source per month |
| `cost_inr` | DECIMAL(12,2) | Simulated monthly channel spend | ≥ 0; campus hiring spikes in season months |

Cost-per-hire requires an attribution assumption (cost month vs. hire month, source
attribution of applications with missing `source_id`). Document any choice before use.

## Canonical definitions used downstream

- **Hire:** an application with `current_status = 'hired'` (equivalently, an application
  with a `hired` stage event). One definition, used everywhere.
- **Application-to-hire rate:** hired applications ÷ total applications in the same
  cohort/period scope.
- **Offer acceptance rate:** accepted offers ÷ offers with a final response (excludes pending).
- **Time-to-hire:** days from `applied_at` to the `hired` stage timestamp; report the
  median alongside the mean because the distribution is right-skewed.
- **Active applications:** `current_status` in (screening, interview, offer). These are
  not drop-offs.
